# V0.1 数据模型与 API

以下为逻辑合同，可映射到 PostgreSQL / MySQL；推荐 PostgreSQL。

## 1. 数据表

### users

```sql
id uuid pk
wechat_openid varchar unique not null
wechat_unionid varchar null
last_alias varchar(32) null
created_at timestamptz not null
updated_at timestamptz not null
```

说明：openid 不通过业务 API 返回客户端。

### capsules

```sql
id uuid pk
creator_user_id uuid not null references users(id)
creator_alias_snapshot varchar(32) not null
statement varchar(160) not null
opens_at timestamptz not null
status varchar(16) not null -- sealed/opened/cancelled
opened_at timestamptz null
opened_by_user_id uuid null
cancelled_at timestamptz null
created_at timestamptz not null
```

### stances

```sql
id uuid pk
capsule_id uuid not null references capsules(id)
user_id uuid not null references users(id)
alias_snapshot varchar(32) not null
stance boolean not null -- true agree / false disagree
submitted_at timestamptz not null
unique(capsule_id, user_id)
```

创建 Capsule 时同事务插入 creator stance=true。

## 2. API

### POST `/v1/auth/wechat`

Request:
```json
{ "code": "wx.login code" }
```

Response:
```json
{ "token": "...", "profile": { "last_alias": "AJ" } }
```

### POST `/v1/capsules`

Request:
```json
{
  "statement": "iPhone 19 还是不会有屏下摄像头",
  "opens_at": "2026-10-18T12:00:00.000Z",
  "alias": "AJ"
}
```

Server validation:
- statement trim 后长度
- alias 长度
- opens_at >= server_now + 10min
- opens_at <= server_now + 2y
- 内容安全

Response: detail DTO，state=`SEALED`。

### GET `/v1/capsules/:id`

SEALED/JOINABLE 响应禁止包含他人 stance。

示例：
```json
{
  "id": "...",
  "statement": "...",
  "creator_alias": "AJ",
  "opens_at": "...",
  "created_at": "...",
  "participant_count": 4,
  "state": "JOINABLE",
  "viewer": {
    "is_creator": false,
    "is_participant": false,
    "my_stance": null
  }
}
```

OPENED + viewer.is_participant=true 时额外返回：
```json
{
  "results": [
    {"alias":"AJ","stance":"agree","is_creator":true,"submitted_at":"..."},
    {"alias":"Rose","stance":"disagree","is_creator":false,"submitted_at":"..."}
  ]
}
```

未参与用户即使 OPENED 也不返回 results。

### POST `/v1/capsules/:id/stances`

Request:
```json
{ "stance": "agree", "alias": "Rose" }
```

事务规则：
1. 锁定/读取 Capsule
2. 必须 status=sealed
3. `server_now < opens_at`
4. 当前用户非已参与者
5. 插入 stance
6. 更新 users.last_alias

重复请求：
- 若同一用户 stance 已存在，返回现有 stance + 200，视为幂等成功
- 不允许用第二次请求修改 stance

### POST `/v1/capsules/:id/open`

允许：viewer 已参与，`server_now >= opens_at`。

推荐 SQL 语义：
```sql
UPDATE capsules
SET status='opened', opened_at=now(), opened_by_user_id=$viewer
WHERE id=$id AND status='sealed' AND opens_at <= now()
RETURNING *;
```

若 0 行：重新读取。
- 已 opened → 返回 OPENED，200
- 未到期 → 409 NOT_DUE
- cancelled/not found → 404/410

### DELETE `/v1/capsules/:id`

仅 creator 且 participant_count=1 时允许。

必须在事务中重新计算参与人数，不能信任客户端。

### GET `/v1/me/capsules?state=&cursor=`

返回当前用户创建或参与过的记录，分页 20。

## 3. 服务端派生状态

```text
if cancelled => INVALID
else if status=opened => OPENED
else if now >= opens_at => DUE for participant; DUE_NON_PARTICIPANT for others
else if viewer participated => SEALED
else => JOINABLE
```

API 可以把 DUE_NON_PARTICIPANT 也输出为 `DUE`，由 `viewer.is_participant=false` 决定 CTA；但前后端合同必须固定一种。

## 4. 并发与一致性

必须测试：
- 两台设备同一用户同时押话
- 多人同时开封
- 截止临界点同时押话/开封
- 撤销与新参与同时发生

数据库唯一约束和条件 UPDATE 是最后防线，不能只靠前端按钮禁用。

## 5. 数据快照原则

历史展示只读 snapshot：
- creator_alias_snapshot
- stances.alias_snapshot

用户后续修改 last_alias 不更新过去记录，确保“当时”语义。
